# GitHub Actions — Caching and Artifacts
## A Complete Beginner-to-Advanced Guide

Welcome to this guide on **Caching and Artifacts in GitHub Actions**.

These two concepts are essential for building efficient CI/CD pipelines. At first, they may look similar because both can help us keep files and reuse them later. However, they solve two different problems.

By the end of this guide, you will understand:

- What caching is and why we need it.
- What artifacts are and why we need them.
- The difference between caching and artifacts.
- How GitHub Actions stores and restores files.
- How cache keys and cache restoration work.
- How to share files between jobs using artifacts.
- How to build a Java Spring Boot application once and reuse its JAR.
- How to use caching and artifacts together in a real CI/CD pipeline.
- Common mistakes and best practices.

---

# 1. The Problem Before Caching and Artifacts

Before learning these concepts, imagine that we have a Spring Boot application.

Our GitHub Actions workflow performs these steps:

1. Download the repository.
2. Install Java 21.
3. Download Maven dependencies.
4. Compile the Java code.
5. Generate a JAR file.
6. Test the application.
7. Build a Docker image.

Everything works correctly.

However, we notice two problems.

### Problem 1: Repeated work

Every time a new workflow run starts, Maven may need to download many dependencies again.

For example:

```text
Workflow Run 1
    |
    +--> Download Spring Boot dependencies
    +--> Download MongoDB dependencies
    +--> Download Testing dependencies
    +--> Compile application
```

Now imagine that we make a small change to one Java file and push it again.

```text
Workflow Run 2
    |
    +--> Download Spring Boot dependencies again?
    +--> Download MongoDB dependencies again?
    +--> Download Testing dependencies again?
    +--> Compile application again
```

Downloading dependencies repeatedly wastes time and network bandwidth.

**Caching helps us avoid repeating unnecessary work.**

### Problem 2: Jobs cannot automatically share their files

Imagine that we have two jobs:

```text
Build Job
    |
    +--> Compile Java application
    +--> Generate app.jar
```

And:

```text
Deployment Job
    |
    +--> Needs app.jar
    +--> Build Docker image
    +--> Deploy application
```

The deployment job cannot automatically access the JAR generated by the build job.

Why?

Because GitHub-hosted runners normally provide separate, temporary machines or virtual environments for different jobs.

The files generated by one job do not automatically appear in another job.

**Artifacts allow us to transfer build outputs between jobs and preserve useful outputs after a workflow run.**

These are the two problems we are going to solve.

# 2. What Is Caching?

Caching means keeping reusable files so that we can use them again instead of downloading or generating them repeatedly.

Think about a student preparing for an examination.

The first time the student studies a topic, they spend time collecting books and notes.

Later, they keep those notes in a bag. When they study the same topic again, they do not need to collect everything from the beginning.

A cache works similarly.

In GitHub Actions:

```text
First Workflow Run
        |
        v
Download dependencies
        |
        v
Save reusable dependencies in cache
        |
        v
Workflow finishes


Next Workflow Run
        |
        v
Look for a matching cache
        |
        +---- Cache found
        |        |
        |        v
        |   Restore dependencies
        |        |
        |        v
        |   Continue build
        |
        +---- Cache not found
                 |
                 v
          Download dependencies
                 |
                 v
             Build normally
```

The purpose is simple:

**Cache reusable files to make future workflow runs faster.**

## 2.1 What should we cache?

Good examples include:

- Maven dependencies.
- Gradle dependencies.
- npm packages.
- Yarn packages.
- pip package downloads.
- Other reusable dependency or build caches.

For example, a Java application may depend on Spring Boot, Spring Web, Spring Data MongoDB, and many other libraries.

Maven stores downloaded dependencies in a local repository, usually:

```text
~/.m2/repository/
```

Without an effective cache, a fresh runner may need to download those dependencies again.

With caching, GitHub Actions can restore previously saved dependency files.

## 2.2 What should we normally not cache?

Do not automatically cache everything generated by a workflow.

For example:

```text
target/
    app.jar
```

If the JAR is the output that we want to transfer to another job, an artifact is normally the appropriate mechanism.

Why?

Because a JAR is a specific build output that we want to identify and consume. A cache is intended primarily to speed up repeated work and may be unavailable when a matching cache cannot be found.

Remember:

- Cache: reusable files that help future runs work faster.
- Artifact: a specific output that another job, person, or process needs.

# 3. How GitHub Actions Caching Works

GitHub Actions caching is not simply a folder that remains available on every runner.

The cache is stored and managed by GitHub Actions. A workflow can request a cache using a cache key.

If a matching cache exists and is accessible, GitHub Actions can restore it.

If no suitable cache exists, the workflow continues without it.

This is important: **a cache is an optimization, not a requirement for your application to work.**

## 3.1 What Is a Cache Key?

A cache key is an identifier used to locate a cache.

Imagine a library containing thousands of bags. Each bag has a label.

If you want your bag, you look for its label.

Cache keys work similarly.

Example:

```yaml
key: maven-${{ runner.os }}-${{ hashFiles('**/pom.xml') }}
```

Let's understand every part.

### Part 1: `maven-`

This is a label we chose ourselves.

It helps identify what the cache is for.

### Part 2: `${{ runner.os }}`

This represents the operating system of the runner.

For example:

```text
Linux
Windows
macOS
```

Keeping the operating system in the key helps avoid accidentally sharing incompatible cached files between different operating systems.

### Part 3: `${{ hashFiles('**/pom.xml') }}`

This calculates a hash based on files matching the specified pattern.

Here, it uses Maven project configuration files.

If a dependency declaration changes in a `pom.xml` file, the hash may change.

That can produce a different cache key.

The resulting key might look conceptually like this:

```text
maven-Linux-a1b2c3d4...
```

The hash shown above is only an illustrative example.

## 3.2 Why Does the Cache Key Matter?

Imagine that your application uses Spring Boot 4.0.7 and MongoDB dependencies.

You save a cache under a key representing your current Maven configuration.

Later, you add another dependency.

Your `pom.xml` changes.

The calculated hash changes, so the workflow looks for a different cache.

This helps the workflow distinguish dependency configurations.

However, an important detail:

**Changing a cache key does not automatically delete old caches, and a cache miss does not mean the build must fail.**

The workflow can download the required dependencies and build normally.

## 3.3 Exact Cache Matches and Restore Keys

The `actions/cache` action supports `key` and optional `restore-keys`.

Consider:

```yaml
- name: Cache Maven Dependencies
  uses: actions/cache@v4
  with:
    path: ~/.m2/repository
    key: maven-${{ runner.os }}-${{ hashFiles('**/pom.xml') }}
    restore-keys: |
      maven-${{ runner.os }}-
```

The `key` specifies the primary cache to look for.

The `restore-keys` provide fallback prefixes.

Suppose the requested key is:

```text
maven-Linux-newhash
```

But the available cache is:

```text
maven-Linux-oldhash
```

The restore prefix:

```text
maven-Linux-
```

may allow GitHub Actions to restore the older cache.

Maven can then download any dependencies that are missing.

This is useful because even if your project configuration changes, some dependencies may still be reusable.

A restore-key match is not the same as an exact match. GitHub Actions may restore an older cache that does not contain every dependency required by the current build.

Also, restore keys are optional. You do not need them for every caching strategy.

# 4. Practical Example: Caching Maven Dependencies

Let's implement caching in a Spring Boot project.

Assume the repository contains:

```text
repository/
|
+-- CICDDEMO/
|   |
|   +-- pom.xml
|   +-- mvnw
|   +-- mvnw.cmd
|   +-- src/
|   +-- Dockerfile
|
+-- .github/
    |
    +-- workflows/
        |
        +-- maven-build.yml
```

Create the workflow:

`.github/workflows/maven-build.yml`

```yaml
name: Maven Build with Caching

on:
  push:
    branches:
      - main

  pull_request:
    branches:
      - main

jobs:
  build:
    name: Build Spring Boot Application
    runs-on: ubuntu-latest

    steps:
      - name: Checkout Repository
        uses: actions/checkout@v4

      - name: Set Up Java 21
        uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'
          cache: maven
          cache-dependency-path: CICDDEMO/pom.xml

      - name: Verify Java and Maven
        working-directory: CICDDEMO
        run: |
          java -version
          ./mvnw -version

      - name: Build Application
        working-directory: CICDDEMO
        run: |
          chmod +x mvnw
          ./mvnw clean package -DskipTests
```

Notice this line:

```yaml
cache: maven
```

The `actions/setup-java` action supports dependency caching. For Maven, it caches the Maven dependency repository.

We also specify:

```yaml
cache-dependency-path: CICDDEMO/pom.xml
```

This is useful because our Maven project is inside the `CICDDEMO` directory rather than at the repository root.

### What happens during the first run?

1. GitHub starts a runner.
2. The repository is checked out.
3. Java 21 is configured.
4. The Maven dependency cache is checked.
5. If there is no matching cache, Maven downloads the required dependencies.
6. Maven compiles and packages the application.
7. The workflow finishes.

### What happens during the next run?

1. GitHub starts a new runner.
2. The repository is checked out.
3. Java 21 is configured.
4. The action looks for a suitable Maven dependency cache.
5. If a matching cache is available, it restores the cached dependencies.
6. Maven uses the restored dependencies and downloads anything still missing.
7. The application is built again.

Notice something important:

**Caching dependencies does not mean caching the final JAR. The application still needs to be built for the current source code.**

Also, caching does not guarantee that every build will be faster. Its benefit depends on dependency changes, cache availability, download costs, and the amount of work the build performs.

# 5. What Is an Artifact?

An artifact is a file or collection of files produced by a workflow that we want to preserve or share.

Think about a factory.

The factory receives raw materials and manufactures a product.

The product is packaged and sent to another department.

In a software pipeline:

```text
Source Code
    |
    v
Build Process
    |
    v
JAR File
    |
    v
Upload Artifact
    |
    v
Another Job Downloads the JAR
    |
    v
Docker Packaging or Deployment
```

The JAR is the product generated by the build process.

GitHub Actions artifacts let us upload that product so it can be downloaded by another job or retrieved later, subject to artifact retention and access rules.

## 5.1 Common Examples of Artifacts

Artifacts can include:

- Java JAR files.
- WAR files.
- Test reports.
- Code coverage reports.
- Compiled frontend files.
- Application packages.
- Diagnostic logs.
- Generated documentation.
- Release binaries.

For example:

```text
Build Job
    |
    +--> app.jar
    +--> test-report.xml
    +--> coverage-report/
```

We can upload one or more of these outputs as artifacts.

## 5.2 Artifacts Are Not the Same as Docker Images

A JAR and a Docker image are different things.

A JAR is a Java application package.

A Docker image packages the application with the filesystem, runtime, and other components specified by its image build instructions.

For example:

```text
JAR Artifact
    |
    v
app.jar
```

Then:

```text
Docker Image
    |
    +--> Java runtime
    +--> app.jar
    +--> Other required files
    +--> Startup configuration
```

A JAR does not automatically include a Java runtime simply because it is a Java application.

The Docker image must provide a compatible runtime, unless the application has been packaged using a different deployment model that supplies its own runtime.

# 6. How Artifacts Work Between Jobs

Let's understand the problem first.

Suppose we have two jobs:

```yaml
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      # Build the application

  deploy:
    runs-on: ubuntu-latest
    steps:
      # Deploy the application
```

These jobs normally run on separate GitHub-hosted runners.

Even though they belong to the same workflow, the deployment job cannot automatically access files created on the build runner.

For example, this file:

```text
CICDDEMO/target/app.jar
```

exists on the build runner after compilation.

It does not automatically appear on the deployment runner.

We need a mechanism to transfer it.

That is where artifacts come in.

```text
                  BUILD JOB
                      |
                      v
                   app.jar
                      |
                      v
                Upload Artifact
                      |
                      v
            GitHub Artifact Storage
                      |
                      v
              Download Artifact
                      |
                      v
                 DEPLOY JOB
                      |
                      v
                 Docker Image
```

Two actions perform the main work:

```yaml
actions/upload-artifact
```

and:

```yaml
actions/download-artifact
```

The upload action publishes the selected files as an artifact.

The download action retrieves that artifact into the current job's filesystem.

# 7. Practical Example: Upload a JAR Artifact

Let's build a complete example.

Assume our Maven project generates a JAR in:

```text
CICDDEMO/target/
```

After a successful Maven build, we upload the JAR.

```yaml
- name: Build Spring Boot Application
  working-directory: CICDDEMO
  run: |
    chmod +x mvnw
    ./mvnw clean package -DskipTests

- name: Upload JAR Artifact
  uses: actions/upload-artifact@v4
  with:
    name: cicddemo-jar
    path: CICDDEMO/target/*.jar
    if-no-files-found: error
    retention-days: 7
```

Let's understand the configuration.

### `name`

```yaml
name: cicddemo-jar
```

This is the name of the artifact.

It is not the JAR's filename. It is the name used to identify the uploaded artifact.

### `path`

```yaml
path: CICDDEMO/target/*.jar
```

This specifies which files should be uploaded.

The wildcard matches JAR files inside the directory.

Be careful: if your project generates multiple JAR files, the pattern could match more than one. If you intend to upload only one executable JAR, verify your build output and use a suitably specific path.

### `if-no-files-found`

```yaml
if-no-files-found: error
```

If no matching file exists, the action fails.

This is useful because we do not want a successful-looking pipeline that silently failed to produce the expected application package.

### `retention-days`

```yaml
retention-days: 7
```

This requests retention for seven days.

Artifact retention is subject to the repository or organization retention limits and applicable GitHub settings.

The artifact is not intended to remain available forever.

# 8. Practical Example: Download the JAR in Another Job

Now we can define a second job.

```yaml
jobs:
  build:
    name: Build Application
    runs-on: ubuntu-latest

    steps:
      - name: Checkout Repository
        uses: actions/checkout@v4

      - name: Set Up Java 21
        uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'
          cache: maven
          cache-dependency-path: CICDDEMO/pom.xml

      - name: Build JAR
        working-directory: CICDDEMO
        run: |
          chmod +x mvnw
          ./mvnw clean package -DskipTests

      - name: Upload JAR
        uses: actions/upload-artifact@v4
        with:
          name: cicddemo-jar
          path: CICDDEMO/target/*.jar
          if-no-files-found: error

  deploy:
    name: Prepare Deployment
    runs-on: ubuntu-latest
    needs: build

    steps:
      - name: Download JAR
        uses: actions/download-artifact@v5
        with:
          name: cicddemo-jar
          path: application/
      
      - name: Display Downloaded Files
        run: |
          ls -lh application/
```

There are two important things here.

### First: `needs: build`

```yaml
needs: build
```

This tells GitHub Actions that the deployment job depends on the build job.

The deployment job waits for the build job to complete successfully before running.

Without this dependency, the jobs could run concurrently, and the artifact might not exist when the second job tries to download it.

### Second: `download-artifact`

```yaml
- name: Download JAR
  uses: actions/download-artifact@v5
  with:
    name: cicddemo-jar
    path: application/
```

This downloads the artifact named `cicddemo-jar` into the `application/` directory.

The filesystem on the deployment runner will look like this:

```text
Runner Filesystem
|
+-- application/
    |
    +-- app.jar
```

The actual JAR filename depends on the Maven build output.

Notice that the deployment job does not need Java 21 or Maven merely to download the JAR.

It needs those tools only if its own steps execute Java or Maven commands.

# 9. The Most Important Example: Build Once, Reuse Across Environments

Now let's connect this to a real CI/CD pipeline.

Suppose we have a Spring Boot application called `CICDDEMO`.

We want:

- One build job.
- One development deployment job.
- One production deployment job.
- A JAR built only once.
- The same JAR artifact made available to both environments.

Our workflow will look like this:

```text
                    PUSH
                      |
                      v
                BUILD JOB
                      |
                      v
               Setup Java 21
                      |
                      v
                 Maven Build
                      |
                      v
                 app.jar
                      |
                      v
                Upload Artifact
                      |
              +-------+-------+
              |               |
              v               v
          DEV JOB          PROD JOB
              |               |
              v               v
       Download JAR      Download JAR
              |               |
              v               v
       Build Docker      Build Docker
       Image             Image
              |               |
              v               v
       Smoke Test        Smoke Test
              |               |
              v               v
       Push to GHCR      Push to GHCR
```

This is a major improvement over independently compiling the application in both jobs.

Why?

Because both environments receive the same JAR produced by the build job.

That reduces unnecessary duplication and helps us keep the application binary consistent.

## 9.1 Complete Workflow Example

The following workflow demonstrates the artifact-sharing pattern. It assumes that the repository contains a working `CICDDEMO/Dockerfile` that copies the JAR from `target/` and that the application listens on port 8080.

It also assumes that the smoke-test endpoint `/get/taha` exists in your application.

```yaml
name: Caching and Artifacts - Build Once Deploy Twice

on:
  push:
    branches:
      - develop
      - main

permissions:
  contents: read
  packages: write

env:
  APPLICATION_NAME: cicddemo

jobs:

  # ======================================================
  # 1. BUILD THE APPLICATION ONCE
  # ======================================================

  build:
    name: Build Spring Boot Application
    runs-on: ubuntu-latest

    steps:
      - name: Checkout Repository
        uses: actions/checkout@v4

      - name: Set Up Java 21
        uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'
          cache: maven
          cache-dependency-path: CICDDEMO/pom.xml

      - name: Build Application
        working-directory: CICDDEMO
        run: |
          chmod +x mvnw
          ./mvnw clean package -DskipTests

      - name: Show Generated JAR
        working-directory: CICDDEMO
        run: |
          ls -lh target/*.jar

      - name: Upload JAR Artifact
        uses: actions/upload-artifact@v4
        with:
          name: cicddemo-jar
          path: CICDDEMO/target/*.jar
          if-no-files-found: error
          retention-days: 7


  # ======================================================
  # 2. DEVELOPMENT JOB
  # ======================================================

  deploy-dev:
    name: Deploy to Development
    needs: build
    if: github.ref == 'refs/heads/develop'
    runs-on: ubuntu-latest

    environment: dev

    steps:
      - name: Checkout Repository
        uses: actions/checkout@v4

      - name: Download JAR Artifact
        uses: actions/download-artifact@v5
        with:
          name: cicddemo-jar
          path: CICDDEMO/target/

      - name: Display Development Configuration
        run: |
          echo "Environment: Development"
          echo "Application URL: ${{ vars.APP_URL }}"
          echo "Debug Mode: ${{ vars.DEBUG_MODE }}"

      - name: Generate Image Tag
        run: |
          echo "IMAGE_TAG=dev-${GITHUB_RUN_NUMBER}-${GITHUB_SHA::7}" >> "$GITHUB_ENV"

      - name: Login to GHCR
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Build Development Docker Image
        uses: docker/build-push-action@v7
        with:
          context: ./CICDDEMO
          push: false
          tags: ghcr.io/${{ github.repository_owner }}/${{ env.APPLICATION_NAME }}:${{ env.IMAGE_TAG }}

      - name: Run Development Container
        run: |
          docker run -d \
            -p 8080:8080 \
            --name cicddemo-container \
            ghcr.io/${{ github.repository_owner }}/${{ env.APPLICATION_NAME }}:${{ env.IMAGE_TAG }}

      - name: Smoke Test
        run: |
          sleep 25
          curl --fail http://localhost:8080/get/taha

      - name: Push Image to GHCR
        if: success()
        run: |
          docker push ghcr.io/${{ github.repository_owner }}/${{ env.APPLICATION_NAME }}:${{ env.IMAGE_TAG }}

      - name: Collect Container Logs
        if: failure()
        run: |
          docker logs cicddemo-container

      - name: Cleanup
        if: always()
        run: |
          docker rm -f cicddemo-container || true


  # ======================================================
  # 3. PRODUCTION JOB
  # ======================================================

  deploy-prod:
    name: Deploy to Production
    needs: build
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest

    environment: prod

    steps:
      - name: Checkout Repository
        uses: actions/checkout@v4

      - name: Download JAR Artifact
        uses: actions/download-artifact@v5
        with:
          name: cicddemo-jar
          path: CICDDEMO/target/

      - name: Display Production Configuration
        run: |
          echo "Environment: Production"
          echo "Application URL: ${{ vars.APP_URL }}"
          echo "Debug Mode: ${{ vars.DEBUG_MODE }}"

      - name: Generate Image Tag
        run: |
          echo "IMAGE_TAG=prod-${GITHUB_RUN_NUMBER}-${GITHUB_SHA::7}" >> "$GITHUB_ENV"

      - name: Login to GHCR
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Build Production Docker Image
        uses: docker/build-push-action@v7
        with:
          context: ./CICDDEMO
          push: false
          tags: ghcr.io/${{ github.repository_owner }}/${{ env.APPLICATION_NAME }}:${{ env.IMAGE_TAG }}

      - name: Run Production Container
        run: |
          docker run -d \
            -p 8080:8080 \
            --name cicddemo-container \
            ghcr.io/${{ github.repository_owner }}/${{ env.APPLICATION_NAME }}:${{ env.IMAGE_TAG }}

      - name: Smoke Test
        run: |
          sleep 25
          curl --fail http://localhost:8080/get/taha

      - name: Push Image to GHCR
        if: success()
        run: |
          docker push ghcr.io/${{ github.repository_owner }}/${{ env.APPLICATION_NAME }}:${{ env.IMAGE_TAG }}

      - name: Collect Container Logs
        if: failure()
        run: |
          docker logs cicddemo-container

      - name: Cleanup
        if: always()
        run: |
          docker rm -f cicddemo-container || true
```

### Important distinction in this example

The workflow above demonstrates how both jobs can download the same JAR.

However, the Docker images are still built independently in the Dev and Prod jobs. Their tags also differ.

For a stronger production design, build and test a Docker image once, push it to GHCR, and promote the exact same image digest between environments.

That gives you:

```text
Build JAR Once
      |
      v
Build Docker Image Once
      |
      v
Push Image to GHCR
      |
      v
Deploy Same Image Digest
      |
      +----> Development
      |
      +----> Production
```

An image digest identifies the image content, unlike a mutable tag that can be reassigned.

Also, this example uses separate branch conditions: `develop` targets `dev`, and `main` targets `prod`. In a real organization, production deployments should generally have suitable environment protection rules, deployment approvals, and carefully restricted permissions.

# 10. Do We Need Checkout in Every Job?

This is an excellent question because it helps us understand what each job actually needs.

Consider this deployment job:

```yaml
deploy:
  needs: build
  runs-on: ubuntu-latest

  steps:
    - name: Download JAR
      uses: actions/download-artifact@v5
      with:
        name: cicddemo-jar
        path: application/
```

There is no checkout step here.

Why can this work?

Because the job only downloads the JAR artifact. It does not need the source repository.

But suppose we add:

```yaml
- name: Build Docker Image
  uses: docker/build-push-action@v7
  with:
    context: ./CICDDEMO
```

Now Docker needs the build context, which includes the Dockerfile and any other files referenced by it.

If those files exist only in the repository, we need to check out the repository or package the necessary files into an artifact.

The structure could be:

```text
CICDDEMO/
|
+-- Dockerfile
|
+-- target/
    |
    +-- app.jar
```

The repository checkout supplies the Dockerfile and other source-controlled files.

The artifact download supplies the JAR.

**A job needs checkout only when its steps need files from the repository.**

# 11. Does the JAR Contain Java 21?

No, not normally.

This distinction is extremely important.

When the build job runs:

```yaml
- name: Set Up Java 21
  uses: actions/setup-java@v4
  with:
    distribution: temurin
    java-version: '21'
```

it configures Java on the runner.

Maven then compiles and packages the application.

The generated JAR contains the application and, for a typical Spring Boot executable JAR, its packaged application dependencies.

It does not normally include a complete Java runtime.

Imagine:

```text
BUILD JOB
|
+-- Java 21 on runner
|
+-- Maven
|
+-- Source code
|
+-- Result
    |
    +-- app.jar
```

Now the deployment job downloads the JAR.

It does not need to install Java if it only passes the JAR into a Docker build.

For example, a Dockerfile might use:

```dockerfile
FROM eclipse-temurin:21-jre

COPY target/*.jar app.jar

ENTRYPOINT ["java", "-jar", "app.jar"]
```

The Docker image supplies the Java runtime.

The distinction is:

- Java 21 on the GitHub runner: needed for the Maven build.
- Java runtime inside the Docker image: needed to execute the application in that container.
- Java 21 setup in the deployment job: unnecessary if the job does not run Java or Maven itself.

---

# 12. Caching vs Artifacts: The Fundamental Difference

Let's compare them directly.

| Feature | Cache | Artifact |
|---|---|---|
| Main purpose | Speed up repeated work | Preserve or transfer outputs |
| Typical example | Maven dependencies | Compiled JAR |
| Reuse | Across suitable workflow runs | Across jobs or later retrieval |
| Identification | Cache key and optional restore keys | Artifact name |
| Exact availability | Not guaranteed | Available while retained and accessible |
| If unavailable | Recreate or download the cached files | The workflow may need to fail or rebuild the output |
| Typical action | `actions/cache` or `setup-java` caching | `actions/upload-artifact` |
| Download mechanism | Cache restoration | `actions/download-artifact` |
| Typical lifetime | Subject to cache eviction and repository limits | Subject to artifact retention and repository limits |

The most important difference is not simply that one lasts longer than the other.

The key distinction is their purpose.

**A cache avoids repeated work. An artifact transfers or preserves a specific output.**

For example:

```text
Maven Dependencies
       |
       v
     CACHE
       |
       v
Faster Future Builds
```

But:

```text
Spring Boot Build
       |
       v
      app.jar
       |
       v
    ARTIFACT
       |
       v
Deployment Job
```

---

# 13. Can We Use Caching and Artifacts Together?

Absolutely.

In fact, many good CI/CD workflows use both.

Consider a Spring Boot application.

We want to download Maven dependencies efficiently and then share the built application with another job.

Our pipeline becomes:

```text
                  BUILD JOB
                      |
                      v
                Setup Java 21
                      |
                      v
             Restore Maven Cache
                      |
                      v
                 Maven Build
                      |
                      v
                    app.jar
                      |
                      v
                Upload Artifact
                      |
                      v
                 DEPLOY JOB
                      |
                      v
                Download JAR
                      |
                      v
                 Docker Build
```

The Maven cache reduces repeated dependency downloads.

The artifact makes the JAR available to the deployment job.

These mechanisms complement each other; they are not competitors.

# 14. Common Mistakes to Avoid

## Mistake 1: Using a cache to transfer the JAR between jobs

A cache is not the right default mechanism for sharing a specific build output between dependent jobs.

Use an artifact when one job must reliably consume the output produced by another job in the same workflow run.

## Mistake 2: Assuming a cache always exists

A cache may not be available because it has never been created, its key has changed, it is inaccessible, or it has been evicted.

The workflow should still be able to build the application without the cache.

## Mistake 3: Forgetting `needs`

If a deployment job requires an artifact produced by a build job, declare the dependency:

```yaml
needs: build
```

Otherwise, the jobs may run in parallel.

## Mistake 4: Using the wrong artifact name

If the upload step says:

```yaml
name: cicddemo-jar
```

the download step must use the same name:

```yaml
name: cicddemo-jar
```

A mismatch means the expected artifact cannot be located.

## Mistake 5: Uploading a path that does not exist

If the Maven project generates its JAR under:

```text
CICDDEMO/target/
```

then this path may be wrong:

```yaml
path: target/*.jar
```

Use the correct path relative to the workspace:

```yaml
path: CICDDEMO/target/*.jar
```

Alternatively, set the working directory appropriately when running the build, while remembering that upload paths are resolved relative to the action's workspace.

## Mistake 6: Installing Java in every job unnecessarily

If the build job compiles the application and the deployment job only downloads the JAR and builds a Docker image, the deployment job does not need `setup-java`.

Install tools according to the operations a job performs, not simply according to the programming language used by the project.

## Mistake 7: Assuming the JAR contains the runtime

A normal executable Spring Boot JAR does not include a complete Java runtime.

Provide a compatible Java runtime in the deployment environment or container image.

## Mistake 8: Rebuilding Docker images independently without considering consistency

If Dev and Prod each build a separate Docker image, the resulting images may differ.

For stronger release consistency, build the Docker image once, push it to a registry such as GHCR, and promote the same image digest between environments.

## Mistake 9: Confusing GitHub Actions artifacts with GHCR images

GitHub Actions artifacts are associated with workflow runs.

GHCR stores container images and their tags or digests.

They serve different purposes:

```text
GitHub Actions Artifact
    |
    +--> app.jar
    +--> test reports
    +--> build outputs
```

```text
GitHub Container Registry (GHCR)
    |
    +--> cicddemo:dev-123
    +--> cicddemo:prod-123
    +--> Container image manifests and layers
```

Use artifacts to transfer workflow outputs. Use a container registry to publish and distribute Docker images.

## Mistake 10: Caching sensitive files

Do not casually cache secrets, credentials, private keys, or other sensitive files.

Cache access and scope matter. Do not place sensitive data in a cache merely because it is convenient.

Similarly, artifacts can be downloaded by authorized users or workflows, so do not upload secrets or private data as artifacts without a justified and secure design.

# 15. Best Practices

For reliable GitHub Actions pipelines:

1. Use dependency caching for Maven, Gradle, npm, and other supported package managers.
2. Use meaningful cache keys based on the operating system and relevant dependency configuration.
3. Treat caches as optional performance optimizations.
4. Upload build outputs using artifacts when another job needs them.
5. Use `needs` to express job dependencies.
6. Use clear artifact names, such as `cicddemo-jar` or `test-reports`.
7. Set an appropriate artifact retention period.
8. Fail the workflow if an essential artifact was not generated.
9. Avoid redundant Java or Maven setup in jobs that do not use them.
10. Build an application once and promote the same output whenever practical.
11. For container-based deployments, consider building the Docker image once and promoting the same immutable image digest.
12. Apply least-privilege permissions to workflow jobs.
13. Protect production environments with suitable approval and deployment restrictions.
14. Never rely on a cache as the only copy of a critical release artifact.

# 16. Quick Revision

### What is caching?

Caching stores reusable files so later workflow runs can avoid repeating unnecessary work.

Example:

```text
Maven Dependencies → Cache → Faster Future Builds
```

### What is an artifact?

An artifact is an output produced by a workflow that we want to preserve or transfer.

Example:

```text
Maven Build → app.jar → Artifact → Deployment Job
```

### What is a cache key?

A cache key identifies a cache to restore.

Example:

```yaml
key: maven-${{ runner.os }}-${{ hashFiles('**/pom.xml') }}
```

### What is `restore-keys`?

Optional fallback prefixes that allow GitHub Actions to search for a suitable older cache when the exact key is unavailable.

### What is `upload-artifact`?

It uploads selected files as a workflow artifact.

### What is `download-artifact`?

It downloads an uploaded artifact into a job's workspace.

### What is `needs`?

It defines a dependency between jobs.

### Does a JAR contain Java 21?

Normally, no. A JAR packages application code and, in a typical executable Spring Boot JAR, application dependencies. A compatible Java runtime must still be available when the application executes.

### Does every job need Java setup?

No. A job needs Java setup when it executes Java or Java-dependent build operations that require that runtime. A job that only downloads a JAR and packages it into a suitable Docker image does not normally need Java installed on its runner.

---

# Final Principle

Remember these two sentences:

**Caching:** Keep reusable files so the next workflow run can do less work.

**Artifacts:** Preserve or transfer the output produced by a workflow so another job or person can use it.

For a Java CI/CD pipeline:

```text
Maven Dependencies
        |
        v
      CACHE
        |
        v
   Maven Build
        |
        v
      app.jar
        |
        v
     ARTIFACT
        |
        v
 Docker Image / Deployment
```

Once you understand this distinction, you can design workflows that are faster, easier to maintain, and more consistent across Development, Staging, and Production.

**Build efficiently. Share outputs deliberately. Deploy consistently.**
